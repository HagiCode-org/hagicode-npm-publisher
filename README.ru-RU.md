# HagiCode npm publisher

[English](README.md) · [简体中文](README.zh-CN.md) · [繁體中文](README.zh-Hant.md) · [日本語](README.ja-JP.md) · [한국어](README.ko-KR.md) · [Deutsch](README.de-DE.md) · [Français](README.fr-FR.md) · [Español](README.es-ES.md) · [Português (Brasil)](README.pt-BR.md) · [Русский](README.ru-RU.md)

Составное GitHub Action, которое публикует пакеты npm из собственного задания вызывающего репозитория с помощью доверенной публикации npm (trusted publishing, OIDC). Один контракт охватывает стабильные релизы, dev-публикации, релизы с несколькими пакетами и диагностику сбоев.

## Почему составное действие

- **Оно выполняется внутри задания вызывающего репозитория.** Шаг публикации использует токен OIDC задания вызывающей стороны, поэтому именно файл workflow вызывающего репозитория запускает `npm publish`. В документации npm составные действия по имени не упоминаются, поэтому это подтверждено реальным запуском, прежде чем на это полагаться; см. [docs/trusted-publishing-notes.md](docs/trusted-publishing-notes.md). Ничего на npmjs.com не меняется, когда репозиторий подключает это действие.
- **Переиспользуемый workflow изменил бы то, кто идентифицируется.** Переиспользуемый workflow публикует из вызываемого задания. В документации npm сказано, что для переиспользуемых workflow проверяется имя *вызывающего* workflow, то есть файл, который вызывающая сторона уже контролирует. Это действие не полагается на такое правило.
- **Без сборки и без зависимостей.** Скрипты — это простой Node ESM в `scripts/`, запускаемый через `${{ github.action_path }}`. Нет каталога `dist/`, который нужно коммитить, и нечего устанавливать до запуска скриптов.

## Быстрый старт

Заданию вызывающей стороны нужны `contents: read` и `id-token: write`, и оно само выполняет checkout репозитория. Составное действие не может задавать права задания.

```yaml
name: npm publish
on:
  push:
    branches: [main]
  release:
    types: [published]

concurrency:
  group: npm-publish-${{ github.ref }}
  cancel-in-progress: false

permissions:
  contents: read
  id-token: write

jobs:
  publish:
    runs-on: ubuntu-latest
    if: github.event_name == 'push' || (github.event_name == 'release' && !github.event.release.draft)
    steps:
      - uses: actions/checkout@v6
        with:
          ref: ${{ github.event_name == 'release' && github.event.release.tag_name || github.ref }}
          persist-credentials: false
      - uses: HagiCode-org/hagicode-npm-publisher@v1
        with:
          mode: auto
          build-command: npm run build
          test-command: npm test
```

Используйте `@v1` для последнего совместимого релиза. Для самого строгого закрепления используйте полный SHA коммита: `HagiCode-org/hagicode-npm-publisher@<40-character-sha>`.

## Входные параметры

| Параметр | По умолчанию | Описание |
| --- | --- | --- |
| `mode` | `auto` | `auto` определяет dev или release по событию. `dev` требует push в ветку. `release` требует опубликованного релиза или push тега стабильной версии. |
| `package-manager` | `auto` | `auto` выбирает pnpm, если `pnpm-lock.yaml` есть в `working-directory`, иначе npm. `pnpm` или `npm`. |
| `node-version` | `24` | Версия Node.js для шага подготовки инструментов. |
| `working-directory` | `.` | Каталог относительно корня репозитория, в котором находятся пакеты и lockfile. |
| `packages` | `.` | Каталоги пакетов, по одному в строке, в порядке публикации. Зависимости ставьте первыми. |
| `provenance` | `true` | Публиковать с `--provenance`. |
| `access` | `public` | Уровень доступа npm: `public` или `restricted`. |
| `dist-tag` | `""` | Переопределяет dist-tag. Пустое значение означает `dev` в режиме dev и `latest` в режиме release. Dev не может использовать `latest`; release должен использовать `latest`. |
| `registry-url` | `https://registry.npmjs.org` | URL реестра npm. |
| `base-version` | `""` | Базовая версия `X.Y.Z` для dev-версий. Пустое значение означает `X.Y.Z` из `package.json` первого пакета. |
| `expected-repository` | `""` | `owner/repo`, из которого должен запускаться workflow. Пустое значение означает текущий репозиторий. |
| `expected-workflow` | `.github/workflows/npm-publish.yml` | Файл workflow, с которым связан доверенный издатель npm. |
| `install-command` | `auto` | `auto` выполняет установку с замороженным lockfile (`pnpm install --frozen-lockfile` или `npm ci`). Любое другое значение её заменяет. Пустое значение пропускает установку. |
| `typecheck-command` | `""` | Команда проверки типов. Пустое значение пропускает этап. |
| `build-command` | `""` | Команда сборки. Пустое значение пропускает этап. |
| `test-command` | `""` | Команда тестов. Пустое значение пропускает этап. |
| `after-version-command` | `""` | Выполняется после проставления версий; заданы `PUBLISH_VERSION`, `PUBLISH_DIST_TAG` и `PUBLISH_MODE`. |
| `registry-neutrality-command` | `""` | Проверка нейтральности реестра, которую поддерживает вызывающая сторона. Выполняется после тестов и до проверок упаковки. |
| `verify-command` | `""` | Проверка, которую поддерживает вызывающая сторона, например проверка графа пакетов. Выполняется до публикации. |
| `pack-check` | `true` | Выполнять `npm pack --dry-run --json` для каждого пакета и отклонять просочившиеся файлы. |
| `verify-package` | `true` | Выполнять общие правила манифеста: точки входа существуют, а в provenance есть совпадающий `repository.url`. |
| `verify-lockfile-stable` | `true` | Завершать с ошибкой, если установка изменила lockfile. Проверяется через `git diff` относительно индекса. |
| `skip-existing` | `true` | Пропускать пакет, версия которого уже есть в реестре. |
| `summary` | `true` | Записывать сводку задания. |
| `stamp-release-version` | `false` | Переписывать `package.json` по стабильному тегу вместо требования, чтобы версия уже совпадала. |
| `dry-run` | `false` | Выполнять все этапы до проверки пакетов, но никогда не вызывать `npm publish`. |

## Выходные параметры

| Параметр | Описание |
| --- | --- |
| `version` | Итоговая версия (dev или стабильная). |
| `dist-tag` | Использованный dist-tag. |
| `mode` | `dev` или `release`. |
| `published` | `true`, если опубликован хотя бы один пакет. |
| `published-packages` | JSON-массив `name@version`, которые были опубликованы. |
| `skipped-packages` | JSON-массив `name@version`, пропущенных, потому что реестр уже содержит их. |
| `package-manager` | `pnpm` или `npm`. |

Выходные параметры записываются даже тогда, когда ничего не опубликовано. Черновик или предварительный релиз устанавливает `published` в `false` и объясняет причину в сводке задания.

## Порядок этапов

Этапы выполняются в фиксированном порядке. Любой сбой до публикации останавливает запуск без публикации. Сводка формируется даже после сбоя.

1. Контекст и валидация: событие, режим, ожидаемый репозиторий и файл workflow, версия и dist-tag.
2. Инструменты: pnpm (если выбран) и Node.js.
3. Установка, затем проверка стабильности lockfile.
4. Проставление версий, затем `after-version-command`.
5. Проверка типов, сборка, тесты.
6. Команда проверки нейтральности реестра.
7. Проверка упаковки, затем проверка пакетов, затем `verify-command`.
8. Публикация, пакет за пакетом, в указанном порядке.
9. Сводка.

`dry-run: true` выполняет этапы с 1 по 7 и никогда не вызывает `npm publish`.

## Контракт версионирования

### Стабильные релизы

Стабильный релиз — это релиз с тегом `vX.Y.Z` (или push тега `vX.Y.Z`). Черновики и предварительные релизы никогда не публикуются. Версия — это тег без `v`, и каждый перечисленный `package.json` уже должен её объявлять. Несовпадение завершается ошибкой до установки. При `stamp-release-version: true` действие сначала записывает версию из тега в каждый манифест — для вызывающих сторон, которые ставят тег до повышения версии.

Стабильные версии публикуются в `latest`.

### Dev-версии

Dev-версия имеет вид `<base>-dev.<run>.<attempt>.<sha>`:

- `<base>` — это `base-version` или `X.Y.Z` из `package.json`.
- `<run>` — это `GITHUB_RUN_NUMBER` (по умолчанию `0`). `<attempt>` — это `GITHUB_RUN_ATTEMPT` (по умолчанию `1`). Оба должны состоять из цифр без ведущих нулей.
- `<sha>` — это `GITHUB_SHA` в нижнем регистре, из которого удалены все символы вне `[0-9a-z]`, затем обрезка до 7 символов.
- Временной метки нет. Номер запуска и номер попытки уже делают версии уникальными и упорядоченными.

Dev-версии публикуются в `dev`. Они никогда не перемещают `latest`.

### Правило префикса `g`

Когда очищенный 7-символьный SHA состоит только из цифр, действие добавляет префикс `g`. `1234567` становится `g1234567`, а `0123456` становится `g0123456`.

Причина — SemVer. Идентификатор, состоящий только из цифр, читается как число. Ведущий ноль делает версию недопустимой, поэтому `npm version` отклонит `X.Y.Z-dev.1.1.0123456`. Короткий SHA только из цифр также сравнивался бы как число, а не как текст. Около 3,7% случайных 7-символьных шестнадцатеричных SHA состоят только из цифр, поэтому это случается в реальных push.

Правило обязательно и покрыто тестами. Префикс добавляется после обрезки до 7 символов. Перед записью чего-либо выполняется самопроверка: итоговая версия должна быть корректным SemVer, а компонент SHA, состоящий только из цифр и без `g`, отклоняется.

## Релизы с несколькими пакетами и связанные релизы

`packages` задаёт порядок публикации. Действие его не сортирует. Каждый пакет получает одну и ту же версию. Точные закрепления между перечисленными пакетами (`"dependency": "0.6.1"`) переписываются на новую версию. Диапазоны вроде `^0.6.0`, `workspace:` и `file:` не трогаются, а предупреждение называет их.

Перед публикацией каждого пакета действие запрашивает у реестра его версии. Версия, которая уже существует, пропускается и записывается в `skipped-packages`, поэтому повторный запуск стабильного релиза может продолжиться с того места, где остановился. Ответ реестра `E404` означает «версий пока нет». Любая другая ошибка реестра останавливает запуск, потому что считать версию отсутствующей никогда не безопасно.

Первый сбой публикации останавливает цикл. Последующие пакеты не пытаются публиковать, поэтому зависимый пакет никогда не уходит раньше своей зависимости.

### Хуки

- `after-version-command` выполняется после проставления версий и до проверки. Используйте его для синхронизации, которой владеет репозиторий, например для версии SDK, которая должна совпадать с проставленной версией.
- `verify-command` выполняется до публикации. Используйте его для правил, которыми владеет репозиторий, например для проверки графа пакетов. Ненулевой код выхода блокирует публикацию.

## Диагностика сбоев

Когда `npm publish` завершается с ошибкой, действие сохраняет вывод npm и код возврата. Затем оно выводит рекомендации для класса ошибки, составленные по имени пакета, `GITHUB_REPOSITORY` и имени файла workflow из `GITHUB_WORKFLOW_REF`. Классы таковы:

- `E404`: убедитесь, что область (scope) npm существует, что публикующая сторона может создать пакет, а доверенный издатель указывает правильного владельца, репозиторий, файл workflow и окружение.
- `E403`: убедитесь, что версия ещё не опубликована и что доверенный издатель разрешает этот запуск.
- `E401` / `ENEEDAUTH`: без переменных OIDC выдайте `id-token: write`. При их наличии проверьте доверенного издателя.
- `provenance`: сравните `repository.url` в `package.json` с репозиторием GitHub.
- `unknown`: общий контрольный список.

Рекомендации выводятся в stderr, в сводку задания и как одна аннотация об ошибке. Токены скрываются из всего, что выводит действие.

## Контрольный список доверенного издателя

Проверьте это для каждого пакета на npmjs.com. Действие не меняет эти настройки.

- Owner: владелец на GitHub, например `HagiCode-org`.
- Repository: имя репозитория на GitHub.
- Имя файла workflow: `npm-publish.yml` (или то, что указано в `expected-workflow`).
- Environment: пусто, если задание вызывающей стороны не использует окружение GitHub и доверенный издатель его не указывает.

Доверенной публикации npm нужен npm CLI версии 11.5.1 или новее и Node.js 22.14.0 или новее. Действие проверяет версию npm CLI перед публикацией и при неудаче завершается с инструкцией по обновлению. Node 24 — значение `node-version` по умолчанию.

## Ограничения

- Спецификаторы `workspace:` не переписываются командой `npm publish`. Манифесты для публикации должны содержать реальные диапазоны версий.
- Версия pnpm берётся из поля `packageManager` в `package.json`. Задайте это поле, когда `package-manager` определяется как pnpm.
- `npm publish` использует `cwd` каждого каталога пакета, а не `--workspace`. Репозитории с одним пакетом и с несколькими пакетами используют один и тот же путь.
- Действие само по себе не запускает сборки и тесты. Это ваши команды, которые передаются как входные параметры.

## Нейтральность реестра

Проверка нейтральности реестра не входит в состав действия. Каждый репозиторий хранит собственную копию, которую поддерживает уже используемый им механизм копирования, и передаёт её через `registry-neutrality-command`. Встроенная копия стала бы вторым источником истины. Пересмотрите это решение, когда изменится механизм копирования или когда вызывающих сторон станет больше нескольких и их копии начнут расходиться.

## Без вспомогательного npm-пакета

Этот репозиторий не публикует npm-пакет. Продукт — это само действие, а манифест помечен как `private`. `scripts/cli.mjs` даёт сопровождающим локальный пробный запуск `resolve` и вспомогательную команду `check-dist-tags`. Добавляйте пакет, только если появится потребитель вне GitHub Actions.

## Теги

Теги `vX.Y.Z` отмечают релизы. Workflow перемещает плавающий тег `v1` только для наивысшей стабильной версии `v1.Y.Z`. Теги предварительных релизов его никогда не перемещают.

## Разработка

```sh
pnpm install
pnpm test
```

Тесты запускают реальные скрипты этапов на пакетах-фикстурах. `npm` и `pnpm` заменяются заглушками в `PATH`, поэтому ни один тест не обращается к реестру. Эталонные (golden) файлы записываются только командой `pnpm run regenerate-goldens`, которая защищена.
